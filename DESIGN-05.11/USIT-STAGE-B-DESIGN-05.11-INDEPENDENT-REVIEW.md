## 2. P0 问题审查

### P0-01｜flock 与 fork 的锁继承语义错误

**涉及位置**：主文档 §1.2、§2.2、§2.5、§7.1。

**原设计问题：**
§1.2 表格将 fork 后的 flock 描述为“子进程不继承”，同时又说明 fork 复制 FD 引用同一 OFD。两项陈述相互矛盾。

在 Linux 的 flock 语义下，锁关联于 open file description。fork 后父子进程的对应 FD 引用同一 open file description，因此子进程继承了该锁关联。关闭子进程自己的 FD 引用不会立即释放仍被父进程引用的锁；但对共享 OFD 调用 LOCK_UN，可能直接解除父进程仍依赖的锁。

**必须修复：**
1. 删除“子进程不继承 flock”的错误描述。
2. 明确区分 FD 表项、OFD、flock 锁及进程所有权。
3. 定义 fork 后父子进程分别允许执行的操作。
4. 明确子进程关闭继承 FD、父进程释放锁、父进程退出、子进程重新 acquire 的完整生命周期。
5. 明确不同 POSIX 平台的语义差异及其验证状态。

**验收标准：**
- 给出父子进程 FD/OFD/锁状态变化表。
- 覆盖父进程先退出、子进程先退出、父子同时运行、子进程调用 LOCK_UN 等场景。
- 不允许出现子进程意外释放父进程锁的情况。
- 未实测的平台必须标记 NOT_VERIFIED。

**结论：FAIL。**

### P0-02｜fork 回调资源清理契约不完整

**涉及位置**：主文档 §2.3、§2.4、§2.6。

**原设计问题：**
`_inherited_lock_fds` 没有定义完整的登记、移除和所有权管理机制；`_in_lock_critical_section` 也没有证明能够可靠识别其他线程是否处于锁临界区。

仅仅注册 `os.register_at_fork(after_in_child=...)`，并不能证明所有继承资源均已被正确处理。

此外，fork 时其他线程可能持有 Python 锁。子进程重建 ProcessMutex 必须考虑回调执行环境、锁状态、注册顺序及第三方库遗留状态。

**必须修复：**
1. 定义继承 FD 的唯一登记和所有权来源。
2. 定义 acquire、release、异常退出、重复释放时的登记更新规则。
3. 定义 fork 前检查机制，不能只依赖未定义的布尔标志。
4. 定义 fork 后 Registry、Lease、Token、ProcessMutex 的完整重置顺序。
5. 明确无法安全处理的场景必须 DENY。
6. 给出多线程持锁时 fork 的处理策略。

**验收标准：**
- 资源登记表与真实 FD 生命周期一一对应。
- 子进程不得复用父进程 Lease。
- 子进程不得对父子共享 OFD 执行 LOCK_UN。
- 不允许子进程继承永久 locked 的 ProcessMutex。
- fork 行为未实测前标记 NOT_TESTED。

**结论：FAIL。**

### P0-03｜路径身份比较仍存在 TOCTOU 窗口

**涉及位置**：主文档 §3.1～§3.4、§7.3。

**原设计问题：**
当前方案先读取句柄身份，再读取路径当前身份，比较一致后允许提交。

但比较完成到后续事务操作之间，路径仍可能被替换。

因此：

`句柄身份 == 路径身份`

只能证明检查时刻的状态，不能证明之后通过路径执行的操作仍然作用于同一个文件对象。

**必须修复：**
1. 明确锁文件所在目录的安全边界及权限要求。
2. 设计基于目录句柄的安全路径操作方案。
3. 评估 POSIX `dirfd`、`openat`、`fstatat`、`O_NOFOLLOW` 等机制的组合使用。
4. Windows 必须定义基于 HANDLE 的对象身份验证与路径操作绑定策略。
5. 禁止只检查路径后再通过可被替换的路径字符串执行关键提交。
6. 锁文件删除、重命名、替换必须有可证明的排他保护。

**验收标准：**
- 覆盖检查后替换、检查后删除、符号链接替换、硬链接及目录路径替换。
- 证明关键操作使用的对象与已验证对象一致。
- 不能证明时必须 DENY。

**结论：FAIL。**

### P0-04｜Windows Candidate 无覆盖提交方案不完整

**涉及位置**：主文档 §4.1～§4.6。

**原设计问题：**
§4.2 提出使用 `CreateFileW(CREATE_NEW)` 创建正式路径空占位文件，再写入内容或进行后续处理。

该方案不能直接证明正式 Candidate 的原子发布：

- 空占位文件可能提前暴露在正式路径。
- 其他恢复流程可能读取到尚未写完的文件。
- 占位文件创建成功不等于 Candidate 内容已完整提交。
- 占位探针与最终发布之间仍需要明确的事务及崩溃恢复协议。

**必须修复：**
1. 区分临时 Candidate、正式 Candidate 和提交占位状态。
2. 优先采用临时文件完整写入、刷新、校验后再无覆盖发布的设计。
3. 明确 Windows 可用的无覆盖重命名或发布原语及其适用系统版本。
4. 明确同卷要求、目标已存在时的失败语义。
5. 明确正式路径不得暴露半成品。
6. 补齐发布前、发布中、发布后各崩溃点的恢复矩阵。

**验收标准：**
- 不允许正式 Candidate 路径出现未完成内容。
- 目标已存在时不能覆盖。
- 发布操作失败不能破坏原有 Candidate。
- 恢复必须验证 transaction_id、candidate_identity、SHA-256 和 revision。
- Windows 行为未经实际验证不得标记 PASS。

**结论：FAIL。**

### P0-05｜Journal Quarantine 审计意图与恢复归因不足

**涉及位置**：主文档 §5.1～§5.8。

**原设计问题：**
当前设计先复制并发布 qfinal，再写审计记录。

如果 qfinal 已发布，但审计记录尚未持久化时进程崩溃，恢复时可能只剩下一个孤立 qfinal。

此时仅凭 qfinal 内容哈希，不能完整证明：
- 它属于哪个事务；
- 它对应哪个原始 Journal；
- 它是否由本次隔离操作产生；
- 是否存在其他事务产生了相同内容。

§5.7 所述“通过 qfinal 内容反推原哈希”不足以解决事务归属问题。

**必须修复：**
1. 增加隔离操作的持久化事务意图。
2. 在发布 qfinal 前持久化 txn_id、源文件身份、源哈希、目标路径及隔离操作 ID。
3. qtmp、qfinal、审计记录必须绑定同一隔离事务。
4. 明确 qfinal 已存在但审计记录缺失时的唯一恢复动作。
5. 明确审计记录写入失败时，不得继续移动原 Journal。
6. 补齐复制中断、发布中断、目录同步失败、审计失败及原文件变化的恢复矩阵。

**验收标准：**
- 任意崩溃点均可识别隔离操作的事务归属。
- 不得仅凭内容哈希推断事务归属。
- 证据不足时保留原 Journal 并 DENY。
- qfinal 不得未经身份和事务校验就被当作有效隔离副本。

**结论：FAIL。**

### P0-06｜Tombstone 删除归因状态与操作顺序矛盾

**涉及位置**：主文档 §6.3～§6.8。

**原设计问题：**
§6.3 对 `REMOVED_BY_THIS_CLEANUP` 的判定要求 tombstone 存在、身份和哈希匹配，并且 REMOVED 已持久化。

但 §6.4 的实际顺序是：

`rename → TOMBSTONED → unlink(tombstone) → fsync → REMOVED_BY_THIS_CLEANUP`

当 unlink 成功、REMOVED 尚未持久化时发生崩溃，恢复时 tombstone 已不存在，无法满足 §6.3 的判定条件。

这说明状态定义和实际操作顺序不一致。

**必须修复：**
1. 重新定义 DELETE_INTENT、TOMBSTONED、UNLINK_INTENT、REMOVED、CLEANED 的状态语义。
2. 明确 tombstone 的创建、持久化、删除和恢复顺序。
3. 明确 unlink 成功但 REMOVED 尚未持久化时的恢复判定。
4. 明确如何排除外部进程删除 tombstone 的可能。
5. 无法证明删除归因时必须使用 INDETERMINATE。
6. 明确 ALREADY_ABSENT 与 REMOVED_BY_THIS_CLEANUP 不得混淆。

**验收标准：**
- 每个状态都有明确的持久化证据。
- 每个崩溃窗口有唯一恢复动作。
- 不得仅凭对象不存在认定本次清理已删除对象。
- 不得出现状态要求 tombstone 存在、实际操作却已经 unlink 的矛盾。

**结论：FAIL。**
